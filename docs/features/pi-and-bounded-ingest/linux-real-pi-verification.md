# Linux 实机 Pi RPC 验证

## 范围

用户指定现有 Linux 服务器进行补充验证，目标是补齐此前 Linux 只有合成
Pi 进程测试、没有真实 Pi RPC smoke 的证据缺口。

- 使用已保存的可信 SSH 主机记录校验身份；没有关闭主机校验。
- 以用户指定的管理账号建立 SSH 连接，但实际 Pi 探针使用既有的非 root
  Pi 运行用户，不把运行时改成 root 来绕过权限。
- 测试源码取自提交 `f1f7a4f1`，含原生 Pi 与有界同步修复。
- 没有启动第二个 Connector、连接 AA Server、部署 wheel、重启服务或升级 Pi。
- 当时进程层设置了空 HOME / agent / cwd，清除继承凭据环境，只发送 `get_state`。
  后续发现现用启动器仍会覆盖 agent 目录，因此本旧记录不作为严格空目录隔离
  的证据；没有发送模型 prompt。修正后的验证见下方升级记录。

## 权限问题与处理

首次在 root 私有临时目录直接调用系统 `pi` 启动器失败。诊断表明启动器使用
`runuser` 切换到既有服务用户；临时审批扩展在宿主上存在，但该用户无法进入
root 所有的 0700 目录，因此 Pi 报扩展路径不可见。

处理方式：

1. 保留首次失败记录，不把它解释为传输协议或模型认证故障。
2. 只调整本次临时目录的属主，保留私有权限；递归操作不跟随系统 Python
   等符号链接，不改变既有项目、安装或账号权限。
3. 用同一既有非 root 用户、原生 Pi 可执行入口与最小环境重跑；该入口的
   agent 目录覆盖限制在后续升级复核中发现，不能仅凭环境变量判定完全隔离。
4. 真实 RPC 成功，子进程回收；没有修改 Connector/Pi 生产代码。

## 数据与资源边界

服务器未预装 uv，也没有可用的系统 pip/ensurepip。因此仅在临时目录使用
经上游发布摘要校验的 uv 工具创建 venv，按仓库镜像安装运行依赖。没有安装
系统包、修改全局包源或用户 shell 配置。本轮不重复全量 pytest，以控制磁盘
占用；之前的 Linux 合成测试记录仍保留，并非用本次 smoke 替代。

测试结束后清理本次目录，保留脱敏结果。未复制真实模型配置、身份凭据、会话
或私有服务地址到仓库。

## 可以与不可以据此声明

可以确认：Windows Pi 1.1.0、macOS Pi 0.87.1、Linux Pi 0.87.1 均已通过当前
原生 Pi 接入代码的真实进程启动、基础 RPC 与进程回收验证。

不能据此声明：三平台的 AA UI → Server → Connector → Pi → 真实模型调用、
流式审批/附件流程都已验收，或所有重连稳定性问题已经解决。此前 Pi 重连状态
测试的波动仍待独立调查；本次结果也不改变 issue #278 完整快照尚未修复的结论。
