# Pi 接入 AA 真实联调记录

## 范围

用户要求"真实补跑，验证真实的参数调整，各项 Pi 功能都能接上 AA 才算通过"。
本次在 Windows 本机用真实组件跑通 AA → Server → Connector → Pi → 模型的完整链路，
不考虑 #278。

| 组件 | 实际使用 |
|---|---|
| AA Server | 本仓库源码，`create_app(db_path=…)` 本地 SQLite，单 worker、无 Redis，仅监听 127.0.0.1 |
| Connector | 本分支源码，`anywhere-cli start`，独立的 home、数据目录和配置 |
| Pi | 本机 Pi 1.1.0（Node 24.14.0），`pi --mode rpc` |
| 模型 | 用户已有的 OpenAI Responses 兼容提供方，两个支持推理的模型；真实调用 |
| 客户端 | 本仓库 Web 客户端 `next dev`，无头 Edge（playwright-core）驱动；另用脚本直接调用 Server API |

隔离措施：

- 本机正在运行的桌面版 Connector 连着正式服务器，测试 Connector 使用独立的
  `USERPROFILE`、数据目录和配置文件，桌面版的运行记录与身份全程未变。
- Pi 使用独立的 agent 目录（`PI_CODING_AGENT_DIR`），模型密钥运行时从原有配置读入
  环境变量，不写入测试目录；会话目录是空的专用目录。
- 未连接正式服务器、未改动用户的 Pi 设置与历史、未安装或替换桌面包。

## 本次修复（Connector）

1. 模型目录按 Pi 规则给出思考等级，选择 id 为 `<provider>:<model>#thinking=<level>`（第二轮审阅后的格式），状态回报同一 id。
2. 只下发有变化的模型和等级，避免每次发消息都在 Pi 会话文件里多写切换记录。
3. 无进程会话的状态从会话文件恢复模型与等级。
4. 扩展命令等待对话框时不阻塞 AA 请求：10 秒接受窗口，后台继续等待，结束后立即发布。
5. 所有 Pi 命令接受自由文本参数；新增内置 `compact`。
6. 附件消息显示用户原文和附件，Pi 仍收到附件说明和图片。
7. 用户消息在本轮开始时流式发布，id 与历史一致。
8. 对话框说明中带上输入框提示和编辑器预填内容。

Mac 上新发现并修复的问题：

1. **AA 的 Pi 进程仍在时，外部 Pi 终端续写同一会话，AA 下一轮从旧位置分叉，终端那一轮
   从时间线和模型上下文中消失。** Pi 没有跨进程写锁。修复后每次写操作前，用会话文件
   最后一条记录的 id 询问活进程（`get_entries since`）；进程不认识该 id 即说明文件被其他
   进程写过，先重开进程再执行。实测：终端写入后会话进程被替换、utility 进程保留，终端
   那一轮保留在当前分支上并排在 AA 新一轮之前；没有外部写入时连续两轮和一次切换选择
   都不重开进程。不支持 `get_entries` 的旧版 Pi 不做重开。
2. **扩展命令在一轮之外写入的消息会短暂出现两次**（流式临时 id 和文件正式 id 各一条，
   直到下一轮整份替换）。修复后一轮之外的消息事件不再流式发布，只在命令结束后从文件发布。

测试脚本层面：macOS 上 Pi 把进程名改为 `pi`，按命令行匹配进程不可靠，Mac 上改按
Connector 的子进程判断。

## 第二轮 Pi 审阅后的修复

用户要求由 Pi（同一模型、xhigh、只读）复审上述修复。提出的 10 项经对照代码核实全部
成立，已修复：

1. 切换权限时，关闭旧进程与启动新进程之间，其他请求可能用旧权限启动进程，AA 显示
   的权限与审批扩展实际使用的不一致。现在两者在同一把启动锁内完成，被替换进程的
   事件和退出回调被忽略。
2. 附件展示按"相同文本取最近一次发送"关联：文字相同的两条消息会显示同一张图；
   Pi 缩放图片时在文本后追加提示，关联还会失败。改为在 Pi 发出用户消息事件时，
   按消息时间戳记录回执。
3. 附件展示与乐观发送绑定共用 200 条上限，长会话会丢失旧附件。带附件的回执现在
   随会话保留。
4. 新会话首次 `get_state` 失败时留下没有会话文件的进程。现在按启动失败处理。
5. 10 秒接受窗口内的命令未计入忙碌，可能被空闲回收；现在从发出起计入。
6. 窗口之后才失败的命令、自动压缩失败只写日志；现在以会话通知告知用户。
7. 扩展 `pi.setModel` 后缓存的模型过期，跳过了真正需要的 `set_model`；现在每轮结束和
   命令结束后读取 `get_state`。
8. `#level` 后缀与模型 id 可能冲突；改为 `#thinking=<level>`，等于目录模型 id 的值
   总按模型处理。
9. DSH 重传成功后，旧的捕获时间可能压不过期间报告的 unavailable，会话仍显示不可用；
   现在恢复时以当前时间重申来源状态（Host 期间报告的归档等事实不覆盖）。
10. 文件尾读取：半行截在 UTF-8 字符中间会抛异常导致发送失败；尾部超出读取预算时
    静默跳过检查。现在半行被跳过，读不到时按需要重开处理。

审阅还指出 fake Pi 与真实 Pi 不一致。fake 现在按模型能力收敛思考等级、用进程内 leaf
续写、能模拟图片提示和慢速/失败命令。更真实的 fake 又暴露一处问题：给不支持推理的
模型设置等级时，Connector 记录的是请求值而不是 Pi 收敛后的 `off`，已改为读回实际值。

真实复核（Windows，Pi 1.1.0，真实模型）：同一文字配两张不同图片（其中一张 4000×4000
触发 Pi 的缩放提示），两条消息各自显示自己的图片和 clientMessageId；回执以 Pi 文件中
的消息时间戳为键持久化，Connector 重启后再发一轮仍保持不变。

## 遗留与未验证

- inputRequest v1 表单没有默认值和多行输入：编辑器预填内容只能显示在说明里，
  网页端把说明显示为一行；输入框表单的选项标为"其他"。改善需要扩展跨端表单契约。
- 本次修改了用户消息 id 规则，已同步会话在文件下次变化时会整份替换一次。
- Server 使用 SQLite、单 worker，没有验证 PostgreSQL/Redis 部署；没有验证正式桌面
  安装包、Android、iOS；Linux 只有自动化测试（WSL），没有做真实联调。
- Windows 真实联调基于提交 `e284d95b`；之后 Mac 上新增的两项修复在 Mac 真实环境和
  Linux/macOS 自动化测试中验证，没有回到 Windows 重跑真实链路。第二轮审阅的修复只在
  Windows 上真实复核了附件回执，其余由自动化测试覆盖（含在旧代码上失败的用例），
  没有在 Mac 上重跑。
- Connector 重启后约 30 秒内，所有运行时实例尚未注册，期间的请求返回
  `unknown runtime instance`。这是 Connector 的通用启动行为，不是 Pi 特有，本 PR 未改。
- 协议 1.0 JSON schema 与客户端生成类型的 runtime 枚举仍不含 `pi`，运行时不校验，不影响使用。
