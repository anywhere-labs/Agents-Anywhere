## 本次修复（Connector）

1. 模型目录按 Pi 规则给出思考等级，选择 id 为 `<provider>:<model>#thinking=<level>`（第二轮审阅后的格式），状态回报同一 id。
2. 只下发有变化的模型和等级，避免每次发消息都在 Pi 会话文件里多写切换记录。
3. 无进程会话的状态从会话文件恢复模型与等级。
4. 扩展命令等待对话框时不阻塞 AA 请求：10 秒接受窗口，后台继续等待，结束后立即发布。
5. 所有 Pi 命令接受自由文本参数；新增内置 `compact`。
6. 附件消息显示用户原文和附件，Pi 仍收到附件说明和图片。
7. 用户消息在本轮开始时流式发布，id 与历史一致。
8. 对话框说明中带上输入框提示和编辑器预填内容。

Mac 上新发现并修复的问题：

1. **AA 的 Pi 进程仍在时，外部 Pi 终端续写同一会话，AA 下一轮从旧位置分叉，终端那一轮
   从时间线和模型上下文中消失。** Pi 没有跨进程写锁。修复后每次写操作前，用会话文件
   最后一条记录的 id 询问活进程（`get_entries since`）；进程不认识该 id 即说明文件被其他
   进程写过，先重开进程再执行。实测：终端写入后会话进程被替换、utility 进程保留，终端
   那一轮保留在当前分支上并排在 AA 新一轮之前；没有外部写入时连续两轮和一次切换选择
   都不重开进程。不支持 `get_entries` 的旧版 Pi 不做重开。
2. **扩展命令在一轮之外写入的消息会短暂出现两次**（流式临时 id 和文件正式 id 各一条，
   直到下一轮整份替换）。修复后一轮之外的消息事件不再流式发布，只在命令结束后从文件发布。

测试脚本层面：macOS 上 Pi 把进程名改为 `pi`，按命令行匹配进程不可靠，Mac 上改按
Connector 的子进程判断。

## 第二轮 Pi 审阅后的修复

用户要求由 Pi（同一模型、xhigh、只读）复审上述修复。提出的 10 项经对照代码核实全部
成立，已修复：

1. 切换权限时，关闭旧进程与启动新进程之间，其他请求可能用旧权限启动进程，AA 显示
   的权限与审批扩展实际使用的不一致。现在两者在同一把启动锁内完成，被替换进程的
   事件和退出回调被忽略。
2. 附件展示按"相同文本取最近一次发送"关联：文字相同的两条消息会显示同一张图；
   Pi 缩放图片时在文本后追加提示，关联还会失败。改为在 Pi 发出用户消息事件时，
   按消息时间戳记录回执。
3. 附件展示与乐观发送绑定共用 200 条上限，长会话会丢失旧附件。带附件的回执现在
   随会话保留。
4. 新会话首次 `get_state` 失败时留下没有会话文件的进程。现在按启动失败处理。
5. 10 秒接受窗口内的命令未计入忙碌，可能被空闲回收；现在从发出起计入。
6. 窗口之后才失败的命令、自动压缩失败只写日志；现在以会话通知告知用户。
7. 扩展 `pi.setModel` 后缓存的模型过期，跳过了真正需要的 `set_model`；现在每轮结束和
   命令结束后读取 `get_state`。
8. `#level` 后缀与模型 id 可能冲突；改为 `#thinking=<level>`，等于目录模型 id 的值
   总按模型处理。
9. DSH 重传成功后，旧的捕获时间可能压不过期间报告的 unavailable，会话仍显示不可用；
   现在恢复时以当前时间重申来源状态（Host 期间报告的归档等事实不覆盖）。
10. 文件尾读取：半行截在 UTF-8 字符中间会抛异常导致发送失败；尾部超出读取预算时
    静默跳过检查。现在半行被跳过，读不到时按需要重开处理。

审阅还指出 fake Pi 与真实 Pi 不一致。fake 现在按模型能力收敛思考等级、用进程内 leaf
续写、能模拟图片提示和慢速/失败命令。更真实的 fake 又暴露一处问题：给不支持推理的
模型设置等级时，Connector 记录的是请求值而不是 Pi 收敛后的 `off`，已改为读回实际值。

真实复核（Windows，Pi 1.1.0，真实模型）：同一文字配两张不同图片（其中一张 4000×4000
触发 Pi 的缩放提示），两条消息各自显示自己的图片和 clientMessageId；回执以 Pi 文件中
的消息时间戳为键持久化，Connector 重启后再发一轮仍保持不变。

## 第三轮 Pi 审阅后的修复

Pi 对 `dbb1604f`、`e7718f9b` 做了第三轮审阅（3 个 P1、5 个 P2），逐条在代码中核对后修复：

- 空闲回收与正在使用会话的请求之间的竞态：请求取用会话时先记一次活动；已被回收的
  会话对象不再启动进程，请求改为重新打开会话。此前可能留下不在注册表中的 Pi 进程。

## 多端联调（Web、Android）

验收标准是多个客户端都能连接 Pi、正确传递参数并调度 Pi。先检查 Desktop、Android、
iOS 客户端如何使用 Pi 依赖的协议，发现三处 Connector 问题并修复：

- Android 修改一项选择时，会把状态回显的全部选择一起发回，旧的 `thinkingLevel`
  覆盖了 `model` 中的新等级。现在以与当前等级不同的一项为准。
- 模型、等级、权限目录没有默认项，Web/Desktop 新建会话会预选第一个模型和 `off`。

## Desktop 开发版联调

本机桌面版切换为开发版（`desktop-workbench`，受管 Connector 运行本分支源码），沿用已安装
桌面版的服务器与 Connector 配置，连接正式服务器，使用本机真实的 Pi 配置（默认
`gpt-6-astra`、`xhigh`）。

- 新建会话预选 `Extra high · gpt-6-astra（<提供方>）`、写入前询问；Pi 会话文件记录的
  模型与等级为 `gpt-6-astra`、`xhigh`。
- 会话内把等级改为 High，Pi 只记录一次等级变化；切换权限（重启进程）后模型与等级保持。
- 每次询问下的工具审批（批准）、等待审批时中断、流式中断、图片附件、`/compact` 带参数
  （会话太小，返回 Pi 的"Nothing to compact"）均通过。
- skill 命令没有在 Desktop 上执行，以免运行本机真实的 skill；逻辑与其他端相同，已在
  Web、Android、Linux、macOS 上验证。

联调中发现并修复一个 Connector 问题：列出运行时类型时，Codex 运行时在事件循环里同步执行
`codex --version`（以及读取登录 shell 的 PATH）。平时每次会让所有运行时停顿最多 5 秒；
这次探测卡死，整个 Connector 失去响应、心跳停止，服务端显示离线，创建会话失败。现在
探测在线程中执行（`main` 上已有的问题，Desktop 每次打开设备页或运行时菜单都会触发）。
Codex 配置校验和运行时启动时的同类探测只在修改配置或启动时发生，留作后续处理。

Desktop 客户端的问题（不在本 PR 处理）：新建会话框每次回到上次或第一台设备的运行时，
多设备时容易选错；会话输入框在连接异常后曾显示另一台设备的 Pi 选择，刷新后正确；
命令执行失败时草稿保留（便于重试）。

## iOS 联调

环境：Mac 升级到 macOS 27.0.1，安装 Xcode 27.0 与 iOS 27 模拟器，以本地临时签名
（`CODE_SIGN_IDENTITY=-`）编译 Debug 版，安装到 iPhone 18 Pro 模拟器，用 idb 操作界面。
连接 Mac 上的本地测试 Server（同一端口同时提供静态 Web，iOS 通过网页完成 OAuth 登录）
与本分支 Connector、真实 Pi 1.1.0。

- 新建会话预选 `gpt-6-astra · Low`、写入前询问（测试环境的 Pi 默认），改为 High 后创建，
  Pi 会话文件先记录默认 `low`、再记录 `high`。
- 切换为每次询问（重启进程）后模型与等级保持；工具审批（批准）、流式中断（回复显示
  "已停止生成"）、skill 命令带参数（`AA-SKILL-OK: hello-ios`）、图片附件（Pi 回答 Red，
  显示原图与原文）、会话内改为 Medium（Pi 只记录一次等级变化）均通过。
- 等待审批时中断：Connector 推送了空闲状态，Server 存储与实时状态都是 `idle`，时间线显示
  已中止；但 iOS 自己发起中断后，输入框一直显示中断按钮，直到下一次状态变化或重启应用
  （中断由其他客户端发起时 iOS 能正常刷新）。这是 iOS 客户端的问题。

模拟器注意点：签名关闭时登录无法写钥匙串（-34018），需要本地临时签名；模拟器默认的
中文拼音键盘会把自动输入的英文当作拼音，测试时只保留英文键盘。

真实 Pi 1.1.0。全部通过：

## 遗留与未验证

- inputRequest v1 表单没有默认值和多行输入：编辑器预填内容只能显示在说明里，
  网页端把说明显示为一行；输入框表单的选项标为"其他"。改善需要扩展跨端表单契约。
- 本次修改了用户消息 id 规则，已同步会话在文件下次变化时会整份替换一次。
- 本地联调的 Server 使用 SQLite、单 worker，没有验证 PostgreSQL/Redis 部署（Desktop
  联调连接的是正式服务器）；没有验证正式桌面安装包；Android、iOS 只在模拟器上的调试包中
  验证，没有在真机上运行。
- Windows 真实联调基于提交 `e284d95b`；之后 Mac 上新增的两项修复在 Mac 真实环境和
  Linux/macOS 自动化测试中验证。第二轮审阅的修复在 Windows 上真实复核了附件回执，
  并在 Mac 复跑中整体复核（见上一节）。
- Connector 重启后约 30 秒内，所有运行时实例尚未注册，期间的请求返回
  `unknown runtime instance`。这是 Connector 的通用启动行为，不是 Pi 特有，本 PR 未改。
- 协议 1.0 JSON schema 与客户端生成类型的 runtime 枚举仍不含 `pi`，运行时不校验，不影响使用。
