# AA v3：加密设备的连接准入与端到端加密（设计稿）

状态：设计稿，未实现，未经密码学审查。总体架构（控制面 + 隧道）另见后续文档。

## 1. 要求

用户明确的要求：

1. **能不能连接，由服务端和设备一起决定。** 两边都同意才建立业务连接；任何一边都能单独拒绝或撤销。
2. **连接只能由物理拿到过配对凭据的客户端发起。** 凭据只在工作设备本机生成和展示（二维码或一次性配对密文），不经过服务端。
3. **服务端不能做中间人。** 即使服务端（控制面、Router、签发方、数据库、网络）完全恶意，也不能读取或篡改隧道里的对话数据和 RPC，不能冒充设备，也不能冒充已配对的客户端。

服务端仍然能做、本方案也不打算阻止的：拒绝服务；看到连接关系、时间、帧大小；看到 Router 路由所需的服务名、方法名和错误码。

## 2. 两道门

| | 服务端门 | 设备门 |
| --- | --- | --- |
| 判断依据 | 账号、设备归属、封禁、配额 | 本机保存的已配对客户端公钥列表 |
| 落在哪里 | 控制面签发隧道凭据（`mtun_e2e.…`），Router 校验凭据、scope、过期和连接数 | Noise 握手：设备从握手消息里拿到客户端静态公钥，自己查表 |
| 撤销 | 撤销隧道，Router 立即断开连接 | 删除公钥，设备立即丢弃这个客户端的所有会话 |
| 单独能做到 | 拒绝连接 | 拒绝连接 |
| 单独做不到 | 让连接成立：没有设备认可的客户端私钥，握手失败 | 让连接成立：没有隧道凭据，到不了设备 |

服务端的同意是必要条件，不是充分条件。服务端不能恢复设备已撤销的客户端，也不能把自己的密钥加进设备的列表。

MeshCall 现有的隧道 offer 钩子（实例同意）仍然保留，但它看到的 `principal` 和 `scopes` 是服务端填的，只能当作服务端门的一部分，不能作为设备门的依据。

## 3. 密钥

- **设备静态密钥**：X25519，工作设备首次启用加密时本机生成，私钥只存在本机（系统钥匙串或权限 0600 的文件）。
- **客户端静态密钥**：每个客户端安装各自生成一对，存在 iOS Keychain / Android Keystore / Desktop 系统钥匙串。同一账号的多个客户端不共享，换机或清数据就要重新配对。
- **配对秘密（PSK）**：32 字节随机数，每次配对单独生成，一次有效，几分钟后过期。

客户端拿到的设备公钥只来自二维码。服务端下发的设备公钥、模式、名称都只是提示，不能用来建立或更新信任。

## 4. 首次配对

1. 用户在工作设备本机打开「添加客户端」。设备生成一次性的配对记录：`pairing_id`、PSK、过期时间，在本机显示二维码。二维码内容：协议版本、设备 `instance_id`、设备静态公钥、`pairing_id`、PSK、过期时间。
2. 客户端扫码，先在本地持久化「这台设备要求端到端加密，公钥是 X」，再向控制面申请一条到该设备的 E2E 隧道（经过服务端门）。
3. 客户端作为发起方，经隧道发起 `Noise_IKpsk2_25519_AESGCM_SHA256` 握手：
   - 用二维码里的设备公钥加密，服务端换不了设备；
   - 握手消息 1 里加密带上客户端静态公钥；
   - PSK 混入密钥，证明发起方看过二维码。`pairing_id` 明文附在握手请求里，供设备找到对应的 PSK；它不是秘密。
4. 设备验证并**原子消费**这条配对记录：已用过、已过期、并发的第二次使用都拒绝。设备本机提示「新客户端已配对」，可要求本机点确认后才生效。之后把客户端公钥写入列表。
5. 握手完成，同一条隧道上即可开始业务调用。

配对窗口内服务端也无法抢先登记自己的密钥：它没有 PSK，握手解不开。

## 5. 已配对连接

之后每条连接用 `Noise_IK_25519_AESGCM_SHA256`（不带 PSK）：

- 客户端用固定的设备公钥发起，没有设备私钥的一方完成不了握手；
- 设备从消息 1 解出客户端静态公钥，不在列表里就以 `e2e_handshake_failed` 拒绝；
- prologue 继续绑定隧道凭据摘要，并加上设备 `instance_id`，经另一条隧道转发的握手打不开。

选 IK 而不是 KK：KK 要求设备在收到消息之前就知道对方是谁，而设备有多个已配对客户端，只有 IK 会在握手里（加密地）告诉设备来的是哪一个。

## 6. 服务端能尝试的攻击

| 攻击 | 为什么不成立 |
| --- | --- |
| 冒充设备，给客户端假公钥 | 客户端只信二维码里的公钥；服务端没有设备私钥，握手失败 |
| 冒充客户端连设备 | 设备只认列表里的公钥；服务端没有对应私钥 |
| 配对时插入自己的密钥 | 没有 PSK；PSK 一次有效且不经服务端 |
| 中间人同时连两边、转发明文 | 两边都认证对方的静态密钥，服务端两段都完成不了 |
| 把一条隧道上的握手或帧挪到另一条 | prologue 绑定凭据摘要和 `instance_id`；帧的 AD 绑定调用、方法、序号和会话 |
| 重放旧帧 | 每方向计数器 + 1024 窗口，重复的拒绝 |
| 降级到明文：谎报设备是普通模式、删字段、发普通隧道 | 客户端本地记住「要求加密」，不接受服务端的更改；设备拒绝一切不在已认证加密会话里的业务调用（见第 7 节） |
| 绕过隧道，用 Router 账号直接定向调用设备 | 同上，设备侧检查，不靠 Router 配置 |
| 设备重装后假称「公钥变了」 | 客户端看到公钥变化只能重新扫码配对，不提供「信任新公钥」按钮 |
| 替换 Web 页面的 JS | 协议挡不住，属于客户端可信分发问题，见第 9 节 |

## 7. 设备侧必须做的检查

- 加密设备上，所有业务服务只在**已完成双向认证的 E2E 会话**里处理调用。非隧道调用、普通隧道调用、未知会话一律拒绝。这一条在设备运行时里判断，不依赖 Router 的 `require_e2e`。
- 每个调用处理器能拿到对端客户端公钥（或设备给它分配的本地 id），按本机授权判断能做什么。服务端填的 `principal` 只用于日志。
- 加密模式的开关只能在设备本机或由已配对且有管理权限的客户端修改。普通改加密：先停掉所有普通入口和现有连接，再接受加密连接。加密改普通：本机明确提示服务端将能看到内容。
- 加密设备不接受服务端 MCP 的控制（MCP 调用天然不在任何已配对会话里，上面第一条就会拒绝）。

## 8. 需要 MeshCall 上游做的改动

MeshCall 现在的 E2E 是 `Noise_NK`，只验证实例，不验证客户端，满足不了第 1 节的要求 1 和 3。需要：

1. 新增握手 profile：`Noise_IK_25519_AESGCM_SHA256` 和 `Noise_IKpsk2_25519_AESGCM_SHA256`。客户端配置自己的静态私钥；配对时额外给 PSK 和 `pairing_id`。
2. 实例侧握手钩子：握手时把客户端静态公钥（和配对时的 `pairing_id`）交给应用决定接受与否，例如 `authorize_peer(peer_key, pairing_id, tunnel) -> bool`。拒绝时返回 `e2e_handshake_failed`，不说明原因。
3. 处理器上下文暴露对端身份，例如 `ctx.e2e.peer_key`。
4. 挂载选项：只接受已认证 E2E 会话里的调用，其余（包括账号直接定向调用）一律拒绝。
5. 客户端可以直接使用自己固定的设备公钥，不依赖签发方给出的 `e2e_key`。
6. 五个运行时（Go、Python、TypeScript、Swift、JVM）都要实现，并在 conformance 里加跨语言测试向量。现有 Noise 是各语言手写的，新增 profile 前要评估改用成熟库。

## 9. 还没定的

1. **Web 客户端**：网页 JS 由服务端下发，服务端换一份 JS 就能读明文。选项：Web 不支持加密设备；或只允许从独立可信渠道分发的 Web（如 Desktop 内置）连接加密设备。
2. **元数据**：是否接受 Router 看到服务名和方法名。不接受就要把所有调用包进一个通用方法，失去类型化契约。
3. **密钥轮换**：设备静态密钥轮换是否支持由已配对客户端在加密会话里授权，还是一律重新扫码。
4. **配对确认**：第 4 节第 4 步是否强制要求设备本机点确认（无人值守的设备做不到）。
5. **推送**：加密设备的通知内容用客户端公钥加密后由服务端转发，具体方案另写。
