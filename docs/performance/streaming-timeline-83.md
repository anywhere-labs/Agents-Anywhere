# 长会话流式更新优化：#83 / #49

本次从上游 `main` 的 `7931ff42885dd4982b3ef156d702d14bfbba8080` 创建分支，提交 PR 前同步到 `c9005d62`，处理已经在本地确认的客户端计算热点。期间新增主线提交涉及 Android 引用块崩溃、桌面进程异常、Windows 路径与 Connector 启动，不改变本报告涉及的合并、去重或审阅函数。关联反馈：[长会话多端卡顿 #83](https://github.com/anywhere-labs/Agents-Anywhere/issues/83)、[服务端逐次全量读取 #49](https://github.com/anywhere-labs/Agents-Anywhere/issues/49)。

## 范围与根因

当前服务端单条 upsert 已使用按 ID 读取及缓冲写入，#49 描述的逐次全量读取并计算会话状态已经不在此基线上。iOS 已有单条更新的二分定位路径。本次不修改服务端、Connector、协议或 iOS。

仍存在的客户端热点：

- Web / Desktop 每次更新一个已有 item，仍重建整段 Map、排序和执行 DSH 去重。
- DSH 去重逐条向前找候选，同一用户轮次内包含较多已完成助手消息时，最坏开销为平方级。
- 普通文字更新导致文件审阅从全部历史重新归并，并重新解析和统计已完成的 diff。
- 未变化的历史 Markdown 缺少组件记忆化，父组件更新时可能重复进入解析渲染。
- Android 在主线程处理实时状态，原有合并会重新分组、排序、去重及合并乐观消息。

这些热点能解释部分计算阻塞，不能证明 #83 中的 DSH 反复重连同源。反馈中压缩会话文件的大小也不能直接换算成客户端 item 数或 diff 大小。

## 实现方案

### 1. 已有 item 的更新快速路径

Web / Desktop 在完成一般合并后，为返回的不可变数组建立 ID 到位置的索引，使用 WeakMap 管理其生命周期。单条更新满足以下条件时，复制数组并替换对应项，沿用位置索引：

- item 已存在，顺序和相邻项排序关系未变化；
- 不涉及乐观消息或用户消息确认；
- 类型、角色和去重相关来源字段没有变化；
- DSH 已完成消息的 hash、状态、旧版 revision 分类没有变化。

不满足条件的更新、初始快照、历史加载和结构变化继续走一般合并。一般合并仅对携带 clientMessageId 的服务端用户消息扫描乐观消息，助手正文不再做这项扫描。旧序号仍遵守原来的拒绝规则，相同序号仍允许后到版本替换。

Android 对已有且顺序稳定的单条助手消息采用相同原则，通常从列表尾部找到目标后，只替换显示行和 ordering 元数据；涉及生命周期、去重字段、顺序变化或特殊行结构时回退。没有乐观消息时，不再额外执行乐观消息合并。

数组和 Kotlin List 仍需复制，因此整体更新仍包含 O(N) 的引用复制；不是整体 O(1)。Android 保留主线程状态提交，本次没有引入后台 reducer 与页面并发更新的竞态。

### 2. 将 DSH 去重改为按轮次的一次扫描

Web、Desktop、Android 都使用两类 hash 索引：

- 原生候选：最近的已完成 `assistant_activity`；
- 旧版候选：最近的已完成、无 itemType 且 revision 大于 1 的助手消息。

遇到用户消息时清空候选索引。原生 `message` 或旧版 revision 为 1 的最终消息查找同 hash 的最近候选。保留显式 replacedBy 规则和原来的最近候选语义，包括已经被标记替代的候选。Android 保留其原有空 hash 不参与去重的行为。

历史排序后的去重由最坏 O(N²) 降为 O(N)，不通过丢弃历史或截断某一轮次来换取性能。

### 3. 文件审阅分两层缓存

- 以不可变 item 对象作为 WeakMap 键，缓存文件变更解析、换行规范化及 diff 增删行数。item 替换后重新计算，旧对象可被回收；不使用无界的全局 ID/string 缓存。
- 每个会话视图维护审阅 selector，只跟踪用户轮次边界、文件变更项、轮次终点、首项顺序、根目录、路径大小写策略和运行状态。普通助手正文内容变化而这些输入不变时，复用上一次审阅结果。

selector 输入是现有合并器产出的有序、唯一、不可变 item 列表。它仍执行 O(N) 的轻量元数据检查，但不会在普通文字更新时重新排序、归并和统计全部历史 diff。历史裁剪、快照替换、文件变更修订、轮次终点改变和运行状态变化会正确失效；需要重建时，未变化 item 的 diff 解析仍可复用。

### 4. 历史 Markdown 组件记忆化

Web / Desktop 使用 React.memo 包装 MarkdownText，输入 props 未变化的历史消息复用渲染。当前正在增长的 Markdown 仍按完整文本解析，保留引用链接等跨段语义；本次不实现增量 Markdown 解析器。

### 5. 历史行分组渲染隔离

2026-10-22 补充浏览器验证发现，仅缓存 Markdown 仍不足以覆盖真实页面：加载全部 569 条构造历史后，10 Hz 流式更新会让历史消息的上下文菜单、附件容器和整行组件持续重新渲染，逐字输入出现自动化按键超时。

Web / Desktop 的会话页现使用独立记忆化分组组件，按分组类型、key、不可变 item 引用及其余全部 props 判断是否需要渲染；代理调用分组同时检查 parentItemId。分组开关回调接收稳定的 key/open 参数，审批回调使用明确依赖的 useCallback。只有变化的分组重新渲染，消息修订、展开状态、审批状态、session、token 或任一回调变化仍会使其失效。公开分享页继续使用原有导出组件与接口。

这一层用于补齐函数基准没有覆盖的 React 工作量，不等同于列表虚拟化，也不减少已加载历史。

## 与初步建议的区别

| 项目 | 初步建议 | 当前实现 |
| --- | --- | --- |
| 按 ID 更新 | 减少全量处理 | 不可变列表上的快速替换，明确去重与排序回退条件 |
| DSH 去重 | 按轮次、hash 建索引 | 原生与旧版两类候选，保留最近候选和 replacedBy 规则 |
| 审阅缓存 | 缓存历史 diff / review | item 解析缓存与视图 selector 分层，明确失效与回收机制 |
| Markdown | 确认重复解析风险 | 复用未变化历史组件，当前消息保留完整解析 |
| Android 主线程 | 减少全量合并 | 缩短同步计算路径，保留主线程提交，不直接异步搬迁状态更新 |

### 2026-10-22 Web 页面验证

使用独立临时 PostgreSQL、当前 Server、当前 Web 的 Next.js 开发服务，以及构造的 DSH 会话。模拟端只提供 Runtime 状态/能力响应；消息更新通过真实 TimelineWriteBuffer、事件广播和 WebSocket 订阅到达页面。没有访问或修改用户的业务会话。
