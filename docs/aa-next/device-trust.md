# 设备安全模式、客户端信任与协议安全目标（T48）

状态：按 M75/M76/M77 更新的设计稿，未实现、未完成密码协议证明或安全评审。两种模式和客户端本地启用要求已由用户明确；不是所有程序实现绝无漏洞的声明。总方案见[架构方案](architecture-proposal.md)。

## 1. 已确定的产品行为

每台工作设备可选择普通模式或 E2EE 模式。客户端也独立保存对该设备的本地安全要求；服务器报告的模式只是发现提示，不能覆盖客户端策略。

| 项目 | 普通模式 | E2EE 模式 |
| --- | --- | --- |
| 连接条件 | 用户身份、设备归属/访问授权和隧道 scope；不要求逐客户端配对 | 账号发现/路由条件之外，每个客户端必须单独配对并证明持有自己的密钥 |
| 未配对客户端 | 可按账号权限连接 | 可看设备在线状态和安全模式提示，不能读取会话、标题、文件或调用业务 RPC；仅允许受限配对入口 |
| 初次接入 | 用户在客户端明确选择普通连接 | 用户在客户端启用 E2EE，扫码或输入工作设备提供的一次性配对密文，建立本地信任 |
| 传输 | 必须 TLS/WSS；Router 可以看到业务内容 | TLS/WSS 内的端到端密文，Router 不持有业务解密能力 |
| 断线/错误恢复 | 重新验证账号与路由权限 | 保持本地 E2EE 要求；重新认证或报错，禁止自动降为普通连接 |
| 云端存储 | 不恢复旧 Timeline 镜像，不持久化/记录正文 | 同样不存正文；服务端内存/转发路径也不能取得业务明文 |

客户端安全要求与设备实际策略共同决定能否访问：两端普通时允许账号直连；两端启用且已配对认证时允许 E2EE；任一端要求 E2EE 而另一端未启用、未配对或认证失败时，拒绝业务连接，不能向较弱模式协商。首次未建立信任时，没有可由云端自动证明真实的设备模式；未知状态不得自动当成普通模式。客户端只有在用户本地明确选择普通模式后才按普通信任模型发送业务。

每个浏览器配置/安装实例是一份独立客户端身份。同账号登录、云端同步设备清单、复制显示名称均不继承配对；清除身份密钥后重新配对。本机 UI 经 OS 用户身份访问本机守护进程，不要求云登录或远程配对，也不受远程租约到期影响。

## 2. 安全性质、假设与攻击者

**协议目标**：两端遵循协议、端点私钥/配对秘密未泄露、随机数和密码原语安全时，控制面与 Router 即使完全恶意，也不能从转发数据恢复业务明文，不能冒充已配对客户端取得业务权限，不能以模式/公钥更新、账号找回、协议协商或重连引导静默降级。

攻击者可控制服务器程序、数据库、账号签发、路由和网络，读取/修改/注入/重放/丢弃任意转发消息，伪造在线状态、设备名称、模式提示和 principal。不能假设服务器运行官方代码或诚实执行 allowlist。服务器可以阻断服务或观察连接关系、长度/时间及仍公开的路由字段；该方案不提供匿名或可用性保证。

必要前提包括：端点执行经审查的协议实现，可信本机生成和展示配对材料，首次传递配对材料的渠道没有被攻击者替换/窃取，OS 密钥保护与加密库正常工作。已修改客户端主动上传明文、失陷终端、用户授权的模型/代理接收内容不属于通信协议能阻止的泄露。

客户端代码来源属于端点信任：如果攻击者同时控制网页分发，可替换 JS 使其不再遵循协议，浏览器不可导出私钥也挡不住恶意 JS 读取明文。这与服务器不能破解协议不同，产品仍须说明可信客户端前提；原生签名/可信更新或独立可信分发 Web 的具体交付方式由方案审阅决定。

成熟算法不能自动证明组合后的流程安全。应选择经分析的认证密钥交换/AEAD 方案，明确协议状态、身份和模式绑定、拒绝条件，给出安全分析与跨端测试向量；完成独立审查前只标记「设计目标」，不宣称已证明绝对无漏洞。计算安全依赖密码学假设，不是对任意实现或无限计算能力的绝对承诺。

## 3. 首次配对与后续认证

1. 用户必须能够接触可信工作机器，在本机生成每个新客户端独立的一次性配对材料并确认授权范围。工作设备本地生成身份及一次性配对材料。二维码与可复制的「一次性配对密文」表达同一配对会话，包含协议版本、目标绑定、有效期和高熵引导秘密；具体握手草案推荐 32 字节随机 PSK。用户通过可信带外渠道传给目标客户端。这个字符串本身是敏感凭据，不能因为 UI 叫密文就上报服务器；不得进入 URL query、遥测、服务端日志或云端剪贴板。
2. 客户端先持久保存「此连接要求 E2EE」，再启动配对。按已分析的带外公钥固定/预共享秘密握手配置建立受保护通道，交换并验证双方身份，把实例、双方身份、模式/协议版本、当前握手及新鲜挑战绑定在认证中。不能依赖 Router 声明的身份或从同一不可信服务器取得的校验公钥。
3. 配对材料只允许一次成功消费：工作设备原子记录使用状态，过期/重放/并发第二次使用均拒绝。材料与具体客户端身份绑定，完成密钥确认并提交本机预先确认的授权后才允许业务；配对失败没有普通业务回退。复制给不同客户端不能产生共享身份或批量授权。
4. 后续每条连接通过双方已固定的身份及新的认证密钥交换建立方向分离的会话密钥，验证对端持钥；不能每次再从控制面接受新公钥。应用证明与加密 transcript/exporter 绑定，使用成熟库，避免另造未分析的签名/加密组合。每个客户端使用独立密钥，撤销一个不影响其他客户端。
5. 配对秘密、私钥及会话密钥只存在端点。长期身份公钥通过带外或端内加密通道交换，无需上传云；Router 使用随机设备/路由标识。标准 Noise 的临时公钥仍明文出现在握手中，PSK 不会自动隐藏它。若连临时公钥也要求不公开，需额外的带外秘密加密封装与分析；不能把 Noise PSK 或外层 TLS 当成此保证。公钥不公开不是业务机密性的必要条件。
6. 每个业务请求及流绑定已认证主体和当前本地授权，使用 AEAD 的认证字段绑定方向、调用/方法与序号，并防重放。设备独立核对 scope、路径和操作权限；账号票据只有发现/路由作用，不能突破 E2EE 模式的本机授权。

当前 MeshCall `9334405` 由 issuer 向 Router 提供 `e2e_key`，且 NK 客户端没有长期身份认证。复用其隧道、加密和流控基础时，需新增端点独立认证/配对及与 Router 解耦的公钥管理；仅隐藏 UI 公钥字段或把现有开关改名不能实现本设计。[具体握手草案](e2ee-protocol-draft.md)推荐首次 XXpsk0、后续 KK 及完成确认，尚未批准 profile/扩展版本，不把草案当成已证明的协议规范。

## 4. 防降级、切换与恢复

- 客户端本地 E2EE 要求和固定身份持久化，服务器不能更新或清除。已配对设备改名、重注册、旧配置重放或恢复备份不能把其重识别为普通设备；身份变化要求重新可信配对。
- 工作设备的 E2EE 开关由本机用户或已配对且具有安全管理权限的客户端确认，不能由普通账号 RPC、控制面配置或 Router 开关关闭。客户端本地安全要求也只能由用户在可信端明确改变。
- 普通转 E2EE：先冻结普通业务入口，持久化新策略，关闭既有普通连接/流并使旧授权上下文失效，再接受已配对 E2EE。每次派发及持续流都检查当前策略，防切换竞态；关闭失败时保持拒绝服务，不在 UI 提前显示保护成功。
- E2EE 转普通：必须明确提示服务器将可见后续传输的业务与可访问历史，并经上述可信确认。关闭不会删除客户端已保存的 E2EE 要求；仍要求加密的客户端拒绝普通连接。已经泄露的普通模式内容也不会因随后开启 E2EE 被收回。
- 密钥异常/丢失、协议不兼容、账号找回和客服操作都不得绕过配对。正确轮换由既有可信身份授权并绑定新鲜会话；身份根丢失须重新配对。不存在服务端解密备用密钥或自动重置用户配对的后门。
- 撤销先在设备持久化，再拒绝请求/关闭流，尽力通知云端。服务器伪造「已撤销/未撤销」不能覆盖本地记录；失联端已下载内容无法保证远程擦除。

## 5. 理论约束对应的验证

| 性质 | 应检查的反例 |
| --- | --- |
| 服务器不持有解密材料 | 配对包、密钥、明文不得出现在 issuer/Router 数据库、日志、诊断、备份或恢复接口；E2EE 旁路均受相同约束 |
| 客户端不能被静默降级 | 服务器谎报普通模式、删字段、重放旧模式、替换公钥、重连/升级失败；客户端在发送首条业务前拒绝 |
| 设备不能被账号身份绕过 | 恶意 Router 任意伪造 principal/scope、开普通隧道、发旧协议或直接调用宿主接口；仍无法读取/执行 |
| 首次信任可验证 | 篡改配对目标、错误秘密、短码猜测、过期/重复/并发消费、串换客户端身份/握手；不能进入已授权状态 |
| 数据完整性与隔离 | 篡改/重放帧、跨调用/隧道搬运、模式切换中未结束的旧流、已撤销客户端继续下载 |
| 无恢复旁路 | 密钥丢失、云账号重置、备份回滚、伪造轮换/授权更新不能复活配对或解密；失败必须可见 |
| 承诺边界一致 | 普通模式明确 Router 可见内容；E2EE 的可信客户端、元数据、模型路径边界如实说明 |

测试证明实现覆盖这些反例，不代替密码协议安全分析；安全分析也不等于所有版本/环境没有实现缺陷。
