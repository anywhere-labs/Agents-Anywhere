# V3 数据格式升级与维护窗口（T48）

状态：评审稿，2026-11-16 起草。本文描述 V3 目标，不描述 2.x 当前行为；不授权实施或上线。

## 1. 依据与已定的方向

- **用户决定（2026-11-16）**：云端升级接受几秒的维护窗口，不追求严格零停机。理由是 V3 的本机工作不依赖云端（M72，主方案第 3 节）：云端短暂不可用只会让远程连接重连，不影响本机历史、终端和 Runtime。
- 主方案已经定下业务数据留在工作设备上（Cloud 的会话 JSON 布局），云端只保留账号、设备、票据、删除标记和运营数据（[数据保留](data-retention-and-cutover.md)第 2 节白名单）。所以「数据库升级」分成三层，难点也和 2.x 不同。
- 2.x 现状作为反例：Server 启动时自动跑迁移，并要求数据库版本**完全等于**代码内置的版本，新旧进程不能同时连同一个库，改代码回退也必须连带回退 schema。Effi Cloud 控制面的迁移执行器（内嵌 SQL、advisory lock、启动时只往前迁）同样没有处理版本兼容；可复用的是执行器写法，不是升级策略。
- 2.x 升级到 3.0 是一次性切换（换新库、只投影白名单数据），按[数据保留与切换](data-retention-and-cutover.md)第 5 节执行，不走本文的常规升级流程。

| 层 | 数据 | 谁来升级 | 本文策略 |
| --- | --- | --- | --- |
| 云端控制面 | 账号、设备、票据、删除待办、运营数据（PostgreSQL） | 运营方，一次一个版本 | 短维护窗口 + 迁移兼容标记，见第 3 节 |
| 工作设备 | 会话、附件、幂等表、排序与设置（本机 JSON） | 每台设备各自升级，时间不一致、可能长期离线或回退 | 读取时逐级升级、保留未知字段，见第 4 节 |
| 客户端 | 本端缓存 | 每个客户端 | 可丢弃，版本不符就清空重取，见第 6 节 |

## 2. 为什么不靠集群解决

集群（多副本 + 负载均衡、数据库高可用）解决的是「有没有进程活着」：只改代码的发布可以滚动替换，数据库主节点故障可以自动切换。它解决不了 schema 兼容：所有副本连的是同一个逻辑库，滚动期间新旧代码同时读写同一套表结构，反而让新旧版本共存成为常态。流复制的从库与主库结构相同；蓝绿双库加逻辑复制不复制 DDL 和序列、改名改类型要自写转换、切换仍要冻结写入，适合一次性大迁移，不适合作为每个版本的常规流程。设备上的数据则根本不在云端集群里。

因此 V3 首版云端可以按需上多副本和托管数据库高可用（部署形态另定），但升级正确性靠第 3、4 节的规则，不靠集群。

## 3. 云端控制面

### 3.1 默认发布流程：短维护窗口

1. 迁移前置检查通过（第 3.4 节），确认本次迁移在窗口预算内。
2. 控制面进入维护：HTTP 返回 `503` 并带 `Retry-After`，新票据与租约续期暂停；Router 和已建立的隧道不受控制面重启影响时继续转发。
3. 停止旧控制面进程，运行一次性迁移任务（与服务进程分开，持 advisory lock，防止两个任务并发）。
4. 启动新进程，健康检查和版本兼容检查通过后退出维护。

窗口预算先定为**单次 10 秒以内**，以生产数据量的演练实测为准；超出预算的迁移不能放进窗口，必须拆成第 3.3 节的在线步骤。迁移连接设置 `lock_timeout` 和 `statement_timeout`，拿不到锁就失败退出、回到旧版本，不让一个卡住的锁把几秒拉成几分钟。

维护期间的表现：本机功能照常；远程客户端显示「服务维护中，正在重连」而不是错误；MeshCall 按已有的退避重连，Router 重启丢失票据时按主方案第 7 节重新注册和取快照。Router 与控制面分开发布，Router 升级不要求跑数据库迁移。

PostgreSQL 大版本升级和换实例也在维护窗口内完成（托管服务的升级或 `pg_upgrade --link`），先在生产副本上演练并测时长；超出预算时另行安排更长窗口并提前告知，不为此常规引入逻辑复制。

### 3.2 迁移兼容标记与代码回退

窗口内停机并不意味着可以放弃兼容：新版本上线后发现问题时，要能只换回旧代码而不回退 schema。规则：

- 每个迁移声明自己是否**破坏上一个版本**（`breaks_previous`）。加表、加可空列、加带常量默认值的列、加索引属于不破坏；删列、改名、改类型、收紧约束、改变既有字段含义属于破坏。
- 服务启动时检查：数据库版本等于自己的版本，或者比自己新、且中间所有迁移都不破坏上一个版本，才允许启动；否则拒绝启动并说明原因。这替代 2.x 的「必须完全相等」。
- 生产环境不使用 down 迁移。回退 = 换回上一个版本的代码，schema 保持不变。
- 破坏性改动拆到两个版本：第一个版本只加新结构并让代码同时兼容新旧（需要时双写），第二个版本再删除旧结构。这样每个版本都能回退到前一个版本。兼容窗口只承诺**前一个版本**。

### 3.3 超出窗口的操作

大表建索引用 `CREATE INDEX CONCURRENTLY`，约束先 `NOT VALID` 再单独 `VALIDATE`，数据回填改为分批、可断点续跑、限速的后台任务，都在维护窗口之前在线完成；窗口内只做元数据级的快速 DDL。V3 云端只有白名单数据，库小、写入少，预计绝大多数迁移不需要这一节，但规则先写下来，避免把慢操作塞进窗口。

### 3.4 发布前的门槛

- 迁移 lint：拦截会长时间持锁的 DDL（如在大表上非并发建索引、原地改类型），并检查 `breaks_previous` 标记与实际 DDL 是否一致。
- 对标记为不破坏的迁移，用上一个版本的代码和测试跑在新 schema 上（「旧代码 + 新 schema」测试）。
- 用生产数据量的副本演练迁移并记录窗口时长；超过预算就不发布，改走第 3.3 节。

### 3.5 实现位置

主方案第 1 节记录 D3 不要求重写现有账号控制面。沿用现有 Python 控制面时，在 Alembic 迁移上加 `breaks_previous` 元数据、把迁移从启动流程拆成独立任务、把启动时的精确版本检查换成第 3.2 节的兼容检查；控制面若改用 Go，则复用 Effi Cloud 的迁移执行器并补同样三处。两种实现规则相同，选择随控制面实现一起决定。

## 4. 工作设备上的数据

设备无法统一协调：成千上万台设备在不同时间升级，可能离线几个月，用户也可能重装旧版本。没有一个能「统一跑迁移」的地方，所以规则必须让每台设备独立、安全地完成升级。

1. **每个持久化文件带格式版本**。Cloud 现有的会话、排序、Agent 设置、会话映射等文件已经写入 `version: 1`，直接沿用。
2. **读取时逐级升级**：每次格式变化写一个纯函数（v1→v2、v2→v3……）。读到旧版本时在内存里依次升级，下一次正常保存时写成当前版本。不在启动时批量迁移，历史再多也不拖慢启动；空闲时可以在后台限速升级没打开的会话。
3. **同一主格式内只做加法**：新增字段一律可选，旧代码读到不认识的字段时忽略，并在改写文件时原样保留。这样用户回退到旧版本后，旧版本不会删掉新版本写入的字段，大多数改动也不需要升格式版本。
4. **只有结构性不兼容才升主格式版本**，第一次写成新主格式前，先给原文件留一份升级前快照（随主方案第 3 节的本地备份规则管理，不进入可同步配置）。
5. **遇到更新的版本就只读**：文件版本高于代码认识的版本时，以只读方式打开并提示「这些数据由更新版本的 AA 创建」，绝不覆盖写入，也不当成损坏删除。
6. **格式进入契约**：每个历史格式版本在 `contracts/` 里保留 fixture，CI 用当前代码加载全部历史 fixture 并检查升级结果。这是设备端的「旧数据 + 新代码」测试。
7. 若按主方案第 3 节的测量结果改用 SQLite，规则不变：版本记在 `PRAGMA user_version`，迁移在打开时的事务内完成，同样只读打开更新版本的库。

**回退政策（提议）**：允许回退到上一个次版本，靠第 3 条保证数据可用；跨主格式回退只能使用第 4 条的升级前快照，快照之后的新数据不保证能被旧版本读取，界面要说明。

**守护进程升级时机**：默认等到没有进行中的轮次再重启升级，重启后按 Cloud 已有逻辑用 `session/load` 接回会话，接不回时显示「会话已中断」；终端由 tmux（Windows 另行适配）持有，不随守护进程重启丢失。是否需要让一个独立 supervisor 在升级期间持有 ACP 子进程和终端，以实测的中断频率决定，不预先实现。

## 5. 多端协议的版本共存

客户端和守护进程会长期版本不一致。Cloud 的同步模型（首快照 + item 整条替换 + control 整体替换）天然适合兼容：item 是文档，新增字段可选，不认识的字段忽略。连接时双方交换协议版本和能力，按双方都支持的能力启用功能，与主方案第 6 节的能力驱动一致。Agent 交互部分直接使用 ACP `initialize` 的 `protocolVersion` 与能力协商，AA 宿主协议沿用同样的模式，不另造版本机制。协议的破坏性变化同样拆两个版本，并在 `contracts/` 中记录最低配套版本。

## 6. 客户端缓存

客户端缓存可以随时丢弃，缓存键包含格式版本；版本不符或解析失败就清空，从守护进程重新取快照。缓存不承担任何需要升级的数据。

## 7. 待确认

| 项目 | 本稿推荐 | 改动时的影响 |
| --- | --- | --- |
| 窗口预算 | 单次 10 秒以内，以演练实测为准 | 放宽则更多迁移可以直接进窗口；收紧则更多迁移要走在线步骤 |
| 云端兼容窗口 | 只保证回退到前一个版本 | 承诺两个版本会让破坏性改动拖长一个版本才能完成 |
| 设备回退 | 次版本可回退；跨主格式只靠升级前快照 | 要求跨主格式无损回退，需要新版本长期以旧格式写入，开发成本高 |
| 控制面实现 | 随控制面实现决定：Python 用 Alembic，Go 复用 Effi Cloud 执行器 | 规则不变，只影响要改的代码位置 |
