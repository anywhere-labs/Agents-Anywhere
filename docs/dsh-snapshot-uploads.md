# DSH 快照上传：内存与恢复边界

原有 checkpoint 记录已成功提交的原生历史位置，能在重新连接后只投影增量；ingest 队列可以重试失败的完整请求。这两者都不记录尚未完成的 HTTP 请求已传了哪些字节，所以不等于快照上传断点续传。

## Connector 内存

Bridge 页面仍按既有规则暂存；超过 8 MiB 时写内部 spool。提交时逐页读取并逐条编码到临时 JSON 文件，再以 64 KiB 块发送。不会把所有页面重新拼成一个列表，也不会生成完整 JSON 字符串或 bytes。实例绑定和 turn 字段过滤保持既有行为。认证重试从文件开头重读；成功、失败和取消都关闭临时文件。

自动化验证 512 条 Unicode 消息合成超过 32 MiB 的正文：编码与哈希阶段的 Python 分配峰值低于 2 MiB。此数值不包含 Bridge 原生投影、页缓存与 item ID 去重集合，也不是操作系统 RSS；服务端目前仍完整解析 JSON，不能据此宣称端到端内存有界。

## 分块续传

Server/Connector 2.2.0 使用独立分块传输接口，契约见 `contracts/connector-snapshot-upload/1.0`。正文排序和编码确定，同一份历史在重连后仍得到同一 SHA-256。来源观测时间 observedAt 不参与上传正文；状态事实仍保留，既有服务端在提交时生成观测时间。快照原生 throughSeq 写入正文并与 manifest 一致。

256 KiB 分块持久化后确认；begin 返回已确认分块和完成 receipt。客户端跳过已确认块。即使块已入库而响应丢失，也无需再传该块。最终收到所有块、核对摘要和来源绑定后，服务端先校验所有历史条目，再将会话元数据、来源状态、完整历史替换、完成 receipt 与暂存块删除放在同一个数据库事务中。成功提交后才发布事件。校验或事务写入失败不会留下部分更新；pending 上传和分块保留，允许重试。数据库提交成功但回复丢失时，重复 begin/commit 读取完成 receipt，不重写历史，也不会提前推进 checkpoint。

恢复仍需读取原生历史和编码临时文件；变化后的历史不复用旧上传。暂存配额、有效期、跨 Connector 隔离和 supersede 规则见契约。Server 启动及每小时清理超过 24 小时的暂存和完成 receipt，级联删除分块；无需等待客户端再次发起上传。最高快照序号单独持久化，不随分块和 receipt 过期，防止清理后旧快照重新获得提交资格。这是 HTTP 快照传输续传，与已成功历史的 checkpoint 增量恢复不同。

## 验证记录

- Python 3.12：Connector 全套 1081 项通过，相关 Server/迁移/生命周期检查 141 项通过；插件 195 项通过，类型检查、构建和产物检查通过。
- 实际 HTTPX/ASGI 与 SQLite 集成：分块 0、1 入库后丢失响应，旧历史保持完整。关闭旧 Store，重建 Server 和 Connector 后只传第 2 块；最终正文正确、重复提交不新增 session revision。另覆盖乱序/缺块、内容冲突、隔离、失效、配额及迁移。
- 小数据故障注入：坏历史出现在首、中、尾位置均在写入前拒绝；历史写入、receipt 保存、暂存块清理中途失败或取消时全部回滚。另覆盖新会话及项目创建回滚、成功回复丢失后的重启恢复、并发重复 commit、提交后事件发布及发布失败恢复、别名解析与用户标题和归档保留。
- 本次失败边界修复的本地验证：32 项快照上传测试（新增 22 项）、7 项 revision fence 回归、15 项会话与架构回归、6 项 Connector checkpoint/ACK 测试，共 60 项通过。使用独立临时 SQLite、小数据和串行测试；单个测试进程观察到的最高 RSS 约 298 MiB，没有运行浏览器或大历史压力测试。新增提交路径遗漏的实时去重缓存失效已通过先失败、后通过的用例修正。
- 同规模约 32.2 MiB 合成 spool，在两个独立 Python 3.12 进程中比较提交阶段：旧实现 Python 分配峰值约 75.5 MiB，新实现约 8.4 MiB；进程峰值 RSS 约 151 MiB 与 92.7 MiB。RSS 包含进程启动和捕获阶段，样本结果不代表所有生产历史的峰值。
- 只逐条生成输入的编码测试，32 MiB 正文的 Python 分配峰值低于 2 MiB；实际 Relay 还会加载最多一页（包括最初不超过 8 MiB 的缓存页），两种测量范围不同。
